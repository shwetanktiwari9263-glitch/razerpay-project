Razorpay AI Payment Recovery • Pitch documentation

1. The pitch

One-line project pitch: Razorpay AI Payment Recovery turns a signed failed-payment webhook into an explainable, tracked recovery path—risk score, cause-aware recommendation, optional payment link, and outcome record—so merchants can act on payment failures instead of merely seeing them.

2. Problem statement

A failed payment is often the end of the visible checkout journey for a merchant. The merchant may know that a payment failed, but not what response is appropriate: wait and retry, ask the customer to authenticate, offer another method, issue a new payment link, or involve support. Repeating the same action for every failure can be ineffective and creates poor customer experience.

3. Why it matters to merchants

  • Each failed checkout can become lost revenue unless there is a clear, timely next step.
  • Error messages alone are technical and fragmented; operational teams need an interpretable recovery recommendation and a record of what happened.
  • Merchants need to distinguish a potentially temporary issue (for example, a timeout) from a customer-action issue (such as invalid card details or insufficient funds).
  • They also need accountability: event, insight, strategy, action, and final outcome should be traceable.

4. Our implemented solution

The project is a local, full-stack payment-recovery workflow. It accepts Razorpay-style payment webhooks, verifies the HMAC signature, stores the event, analyses failed payments, records a recovery recommendation, optionally creates a Razorpay Payment Link when credentials are configured, and marks the recovery successful when a uniquely matching captured-payment webhook arrives.

Scope honesty: SMS, email, and customer-support delivery are recorded as pending channel actions; the code does not send them. A retry is a recommendation with a stored strategy—not an automatic charge retry. Without Razorpay credentials, a clearly labelled mock payment-link identifier is stored and remains pending. Groq advice is used only when configured; otherwise deterministic rules are used.

5. End-to-end workflow

Razorpay payment.failed webhook ↓ (raw body + X-Razorpay-Signature verified with HMAC-SHA256) Spring Boot webhook endpoint → payment_events (idempotent event_id) ↓ SystemInsightService → ML FastAPI/scikit-learn score OR rules fallback ↓ + error-text root-cause categorisation AiAgentService → Groq structured recovery advisor OR deterministic rules ↓ RecoveryActionService → record action; create Razorpay Payment Link only for payment_link recommendations and configured credentials ↓ recovery_outcomes = PENDING ↓ Razorpay payment.captured webhook → uniquely match by replacement payment ID, or matching order ID + amount → mark SUCCESS, amount and recovery time

8. Razorpay integration and webhook flow

The code expects payment.failed and payment.captured-style payloads. It retains the raw payload, normalises amount from paise to INR, maps status, and captures Razorpay identifiers, payment method, bank/wallet, error code, error description, and customer ID when available. Live links require RAZORPAY_KEY_ID and RAZORPAY_KEY_SECRET. The webhook secret is injected through environment configuration, never hard-coded.

Demo-safe wording: “This project integrates with Razorpay webhooks and has a real Payment Link API call path. In my local demonstration, credentials determine whether the link is real; the application labels the mock case honestly.”

9. ML component and prediction flow

The Python service loads failure_predictor.joblib and exposes POST /predict. It builds categorical and numeric features including transaction type, merchant category, sender/receiver attributes, bank, network, time, amount, fraud flag, weekend, peak-hour, night, and high-value flags. The training script uses a stratified 80/20 split of the included 250,000-row UPI dataset and trains a preprocessing pipeline plus HistGradientBoostingClassifier.

The Java backend calls this service when ML_SERVICE_ENABLED=true; any model-service failure falls back to recoverflow-rules-v1. The rules return probability, risk factors, risk level, and a confidence label. The ML endpoint returns a probability and labels its confidence as “medium”; it does not claim calibrated confidence intervals.

Model-quality disclosure for judges: the committed report records test ROC-AUC 0.490147 and average precision 0.048756. These figures do not support a claim of strong predictive performance. Present the ML service as a functioning, replaceable scoring pipeline and rules fallback—not as a production-validated predictor.

10. AI / rule-based payment recovery mechanism

First, the backend categorises the Razorpay error description/code into root causes. Then it uses Groq, if a key is configured, to create structured advice that is explicitly prohibited from predicting payment outcome. If no valid AI response is available, the rule engine creates a deterministic explanation, confidence, priority, recommended channel, recovery steps, alternatives, and retry-policy metadata.

Detected causeExamples of implemented channel / advice
Insufficient funds, repeated failures, customer issueCustomer support: resolve the customer-side issue rather than blindly retrying.
Invalid/expired card, UPI failure, bank or gateway issue, unknownPayment link: ask for updated details or a retry with alternatives; link creation is configuration-dependent.
Authentication failure, timeout/network, rate limitRetry recommendation with a stored retry strategy; rate-limit advice waits longer. No automatic payment charge is performed.

11. Frontend and dashboard

  • Dashboard: selectable period, total/successful/failed/recovered counts, recovered amount, average recovery time, risk distribution, top issue, error-code distribution, payment-method failure rate, recent failures, and up to six recovery-analysis cards.
  • Payments: paginated and status-filtered event list. The details modal has Info, ML Prediction, and AI Analysis tabs. ML/AI tabs correctly report unavailable data for unprocessed/non-failed events.
  • ML Predictor: form inputs to request an estimate before a payment attempt. The screen explicitly says it does not generate AI recovery advice.

12. Database architecture

payment_events ├─ system_insights (failure probability, category, metadata) ├─ ai_agent_analysis (cause, explanation, channel, strategy, reasoning) └─ recovery_actions (execution state, link ID/error, metadata) └─ recovery_outcomes (pending/success, recovered amount, duration) └─ new_payment_event_id → payment_events (captured event) MySQL views: v_recovery_pipeline joins the journey; v_recovery_metrics aggregates daily attempts, successes, amount and time.

The schema stores JSON for raw payloads and flexible strategy/metadata, uses foreign keys, timestamped records, and indexes for event IDs, payment/order IDs, status, channels, and outcomes.

15. What makes it different

  • Recovery is cause-aware: it maps a failure to a channel and explicit next steps rather than offering one generic retry.
  • Separation of roles: prediction estimates risk; Groq/rules recommend recovery. The Groq prompt explicitly prevents it from inventing a payment prediction.
  • Closed-loop design: it stores the original event, insight, advice, action, and eventual capture outcome in linked records.
  • Honest execution state: mock versus executed payment links and pending non-integrated channels are not disguised as completed actions.
  • Operational visibility: dashboard and reporting views connect individual failures to aggregate recovery metrics.

16. Business impact

The implemented value is operational: faster triage, consistent recovery playbooks, a path to recovery links, and a measurable recovery trail. It is designed to help a merchant focus attention on failed-payment follow-up. It does not establish a measured uplift in recovery rate or revenue yet; that requires live, governed operating data and evaluation.

17. Realistic end-to-end demo scenario

Scenario: A customer’s ₹1,250 UPI payment for order_demo_001 is declined with a bank-decline description. A signed payment.failed webhook enters the backend. The system stores it, classifies it as a bank issue, produces a risk score, creates a cause-aware payment-link recommendation, and records a pending recovery outcome. If Razorpay credentials are configured, it requests a real Payment Link; otherwise it visibly remains a mock/pending action. When a later captured webhook with the same order and amount arrives as the only eligible candidate, the outcome becomes success and records ₹1,250 plus elapsed recovery time.

Never say: “The system automatically retries the customer’s card,” “we sent an SMS,” or “we recovered real merchant revenue.” Those are not supported by this codebase.

21. Fifteen likely judge questions and strong answers

QuestionAnswer
Is this just a retry system?No. It classifies failure context and selects a recovery channel and steps. It distinguishes, for example, timeout from expired card or insufficient funds, and records the entire decision and outcome trail.
Does it automatically retry a charge?No. The current version records retry advice and strategy but does not re-charge the customer. That is deliberate scope control.
What is actually AI here?The implementation has an optional Groq structured recovery advisor. It is constrained to advise on recovery, not to predict payment outcomes. It falls back to deterministic rules for reliability.
What does the ML model predict?Failure probability from transaction features. The same backend has a rule-based fallback if the local ML service cannot respond.
How accurate is the model?The committed report has weak holdout discrimination—ROC-AUC 0.490147. I would not claim production accuracy. The functioning pipeline is ready for better data, calibration, and governed evaluation.
How do you secure webhooks?HMAC-SHA256 on the exact raw body, configured secret, constant-time comparison, and rejection of invalid signatures. Unsigned acceptance is an explicit local-only setting.
How do you avoid duplicate events?The Razorpay event ID is unique in the schema and checked before saving. Duplicates return a duplicate status rather than rerunning recovery.
Does it send SMS or email?No. Those channels are stored as pending recommendations. The code does not claim provider delivery.
Does it create a real Razorpay link?It has a real REST call path to Razorpay Payment Links when test/live credentials are configured. Without credentials it creates a labelled mock link and leaves it pending.
How is recovery success determined?On a later captured webhook, it matches the expected replacement payment ID or same order plus amount. It closes the outcome only when exactly one pending candidate matches.
Why use both ML and rules?ML provides a service boundary for probability scoring; rules give predictable behavior, explainability, and continuity if the model service is unavailable.
Why separate AI advice from prediction?It avoids asking a generative model to invent financial probabilities. The advisor receives the existing score and error context only to choose recovery guidance.
What does MySQL store?Raw event, insight, analysis, action, and outcome records linked by foreign keys, plus audit metadata and reporting views.
What was tested?18 backend tests passed and the frontend production build passed. The MySQL integration test is present but was not run without its explicit database prerequisite.
What is the next validation step?Run the opt-in MySQL integration test and Razorpay Test Mode workflow, then evaluate recovery strategies on real, consented operational data before making business claims.
